## 0. 命名决议

采纳「Trader OS」，弃用「Trading Coach」作为模块名。

理由不只是"Coach 有指导意味"，更硬的理由是**命名体系一致性**。实测 `backend/os_layers/` 现有四个：

```
data_os.py  research_os.py  decision_os.py  learning_os.py
```

Trader OS 作为第五个 OS 层，与既有命名同构，代码落位为 `backend/os_layers/trader_os.py`。「Coach」降级为其下属 Agent 之一。

```
Trading OS
├── Data OS            已有
├── Research OS        已有
├── Decision OS        已有
├── Learning OS        已有
└── Trader OS          本文档，新增
    ├── Trade Memory     记录
    ├── Execution Audit  审计
    ├── Trading DNA      画像
    └── Coach Agent      反馈
```

## 1. 边界冻结（永久约束，不随版本变更）

### 1.1 Trader OS 永不做的事

| 禁止项 | 性质 |
|---|---|
| 产生买卖建议（标的 + 方向） | 永久禁止 |
| 修改任何 Layer1 评分模型参数 | 永久禁止 |
| 写入 `regime_history` / `sector_daily` 等 Research 层表 | 永久禁止 |
| 盘中实时推送 | 永久禁止 |
| 在样本未达闸门时降级输出结论 | 永久禁止 |

前四条是设计红线。第五条是数据纪律，与既有「诚实 NULL > 伪精确」治理偏好一致。

### 1.2 Trader OS → Decision OS 接口：单向阻断

**冻结条款：Trader OS 对 Decision OS / CIO 的写接口不存在，且不预留。**

不是"前 100 笔不接"这种可以后来放宽的软约束，而是代码层面不提供该接口。要接必须改架构，改架构必须走 §9 解冻流程。

用户提出的三阶段（0-200 观察 / 200-500 反思问题 / 500+ 风险提醒）方向认同，但需修正一处**内部矛盾**：既说"永久保留不接 CIO"，又说"500 笔后开风险提醒层"。这两句不能同时成立，除非明确"风险提醒"的投递对象。

冻结版的处置：

| 阶段 | 门槛 | 输出 | 投递对象 |
|---|---|---|---|
| 观察期 | 0-200 笔 | 描述统计 | 人（周报） |
| 反思期 | 200-500 笔 | 反思问题（不含结论） | 人（周报） |
| 提醒期 | 500 笔以上 | 风险提醒 | **人，不是系统** |

关键澄清：**风险提醒永远投递给人，不投递给 CIO。** 这样"永久不接 CIO"与"三阶段演进"就不冲突了。CIO 永远不知道 Trader OS 的存在。

关于 500 笔门槛的现实性提醒：按 A股侧当前 0 笔起步，若月均 5 笔，500 笔需 8 年。所以门槛必须**按市场独立计数**，且 A股侧大概率永远停在观察期。这不是缺陷，是诚实。

## 2. 数据流冻结

采纳用户提出的 Decision Snapshot 层。这是本轮评审最有价值的补充。

```
┌─────────────────────────────────────────┐
│  Market State Snapshot                  │  Research OS 产出
│  regime / sector / flow  当日客观事实      │  已存在
└──────────────┬──────────────────────────┘
               │  T 时刻冻结，此后只读
               ↓
┌─────────────────────────────────────────┐
│  research_decision_log                  │  事前：我打算做什么
│  已存在（3 条）                           │  hypothesis / invalidation
└──────────────┬──────────────────────────┘
               ↓
┌─────────────────────────────────────────┐
│  decision_snapshot          ★ 新增       │  当时知道什么
│  信息封存，防后视偏差                      │  见 §2.1
└──────────────┬──────────────────────────┘
               ↓
┌─────────────────────────────────────────┐
│  trade_execution            ★ 新增       │  事后：我实际做了什么
│  market_type ∈ {ASHARE, MT5}            │
└──────────────┬──────────────────────────┘
               ↓
┌─────────────────────────────────────────┐
│  outcome                                │  结果回填
│  延后，依赖平仓                            │
└─────────────────────────────────────────┘
```

`trade_journal`（121 条信号）作为 Research OS 的信号输出侧表保留原位，Trader OS 只读不写。

### 2.1 Decision Snapshot 的真正难点：不是存储，是隔离

用户指出「AI 复盘必须只看到当时信息，不能看到未来价格，否则变事后诸葛亮」。方向完全正确，但**光存快照解决不了这个问题**。

原因：快照存在同一个数据库里，分析 Agent 一条 SQL 就能查到快照之后的价格。防后视偏差需要的是**查询层强制隔离**，不是数据层被动留存。

冻结的工程约束：

| 机制 | 说明 |
|---|---|
| `as_of_date` 强制参数 | 所有 Trader OS 分析函数必须接收该参数，无默认值 |
| 查询包装层 | 数据访问统一走 `snapshot_query(as_of_date)`，内部对所有涉及日期的表自动追加 `WHERE date <= as_of_date` |
| 禁止裸 SQL | Trader OS 内禁止直连 sqlite3 执行未包装查询，Code Review 红线 |
| 快照哈希 | 每条 snapshot 存生成时的内容哈希，事后篡改可检出 |

这条约束的重要性等同于既有的「§14 观察≠验证，禁未来函数」治理红线，属同类问题在 Trader OS 侧的实例化。

### 2.2 快照内容（A股 / MT5 通用）

```
snapshot_id / decision_id / as_of_datetime
market_type
regime_state / regime_score          ASHARE: regime_history
                                     MT5: NULL（待全球资产接入）
risk_budget_equity                   ASHARE: cio_decision_history
sector_context                       ASHARE: 当日板块资金流 TOP
asset_context                        标的当时价格 / 所属板块 / 排名
reasoning_text                       当时的判断理由，人填
confidence                           1-5
content_hash                         防篡改
```

## 3. 核心指标冻结：CCR 三段漏斗

用户建议把 Plan-Execution Gap 升级为 CCR（Cognitive Conversion Rate），命名采纳。但**公式必须改**，原式有硬缺陷。

### 3.1 原公式的问题（实测数据支撑）

原式：`CCR = 已执行的计划 / 已生成的计划`

若分母取"系统生成的信号"，实测数据如下：

| 日期 | 信号条数 |
|---|---|
| 07-20 | 10 |
| 07-21 | 15 |
| 07-23 | 15 |
| 07-29 | **36** |
| 07-30 | 15 |
| 07-31 | 20 |
| 08-03 | 10 |

合计 121 条 / 7 个交易日 = **17.3 条/天**。

即使按每天实际执行 2 笔计算（对个人投资者已属频繁），CCR 上限 = 14/121 = **11.6%**。

这个数字测量的不是你的认知转化效率，而是**系统信号的冗余度**。分母被系统的产出量绑架，你把信号数调到 50 条/天，CCR 立刻腰斩，但你的执行质量毫无变化。指标失效。

### 3.2 冻结版：四段漏斗（采纳用户命名，修正两处）

用户将 Plan-Execution Gap 升级为 CCR 三段漏斗（Recognition / Decision / Execution），方向采纳。
经本轮复核，确定两处修正：

1. **Recognition 层在 v0.1 不可测，标记 deferred。** 原定义 `Recognition = Seen / Generated` 有两硬伤：分母仍是系统信号量（同原式缺陷）——系统发 100 你看到 80，发 200 你看到 160，你的"信息能力"没变指标却腰斩；"Seen" 客观上不可测——系统无任何信号曝光/打开记录，用户自报"我看到了"是事后噪声。故 v0.1 不产出 Recognition 数值，待信号曝光埋点后启用。
2. **补回 Holding 段。** 用户三层链路在 Execution 终止，但钱在持有阶段亏。原 CCR-3（持有转化）是 A股侧最大漏损点（依据：`action` 121 条全「买」、卖出 0 条，卖出决策完全裸奔），不能丢。漏斗定为四段。

```
系统信号(Generated) ─┐
                     │  Recognition = Seen / Generated     ★v0.1 不可测(deferred)
你看到的(Seen)     ─┘
    │  Decision Conversion = Planned / Seen(可见信号)       测量筛选能力
    ↓
你认可的计划(Planned)
    │  Execution Fidelity = Executed / Planned              ★核心，测下单纪律
    ↓
实际下单(Executed)
    │  Holding Discipline = 按计划持有·退出 / Executed        ★最大漏损点，当前零测量
    ↓
按计划持有到底(Held)
```

| 指标 | 公式 | 测量对象 | 归属 | v0.1 状态 |
|---|---|---|---|---|
| Recognition Rate | Seen / Generated | 信息处理能力 | Research OS 侧 | **deferred（无曝光埋点）** |
| **Decision Conversion** | Planned / Seen | 筛选能力 | Trader OS | 可测（需记录 Planned） |
| **Execution Fidelity** | Executed / Planned | 下单纪律 | Trader OS 核心 | 可测（最小闭环即可） |
| **Holding Discipline** | 按计划持有·退出 / Executed | 持有纪律 | Trader OS 核心 | 可测（需记录退出计划） |

**Execution Fidelity 是用户原意所指，分母必须是你自己认可并写下的计划（不是系统输出）。**
**Holding Discipline 是本轮确认的最大漏损点**——A股个人投资者主要亏损来自持有阶段动作变形（该止损不止、盈利过早了结），当前零测量。

### 3.3 冻结：Recognition / Decision Conversion 的归属边界

- Recognition Rate 分母=系统信号量，低说明系统信号冗余，属 Research OS 信号质量问题，不归 Trader OS，且 v0.1 不计算。
- Decision Conversion 分母=Seen，但 Seen 不可测，故 v0.1 务实定义为 `Planned / 当日候选池可见信号数`（以用户可见信号为近似）。把它算成"你的认知转化率"会导致归因错位：系统多发信号 → 你的"转化率"下降 → 误判自己纪律差。

这条边界必须冻结。

## 4. 行为状态标签：采纳，加两条约束

用户反对完全删除情绪字段，改用离散行为状态标签。**这个修正我接受**，我原判断过度了。

区别确实成立：
- 「你感觉如何」= 连续量表 + 事后自评 = 噪声
- 「你当时处于什么交易状态」= 离散标签 + 开仓前记录 = 可分析

标签集冻结为 5 个，单选，不可扩展（扩展需走 §9）。用户 2026-08-04 第二轮调整为 `normal/hesitant/urgent/revenge/fomo`，并明确**最低优先级——若增加记录负担立即删除**：

```
normal      正常
hesitant    犹豫（拿不准）
urgent      紧急（被迫出手/被扫）
revenge     报复性（亏损后立刻再交易）
fomo        追赶（怕错过）
```

> 说明：此字段目的不是分析心理，而是未来验证「状态是否影响执行质量」。优先级最低；A0 最小闭环不强制填，留空即 NULL。约束一（开仓前记录）与约束二（交叉验证）仍适用，见 §4.1/§4.2。

### 4.1 约束一：必须开仓前记录

事后补记的状态标签仍有结果偏差，与情绪自评同病。工程实现上：状态标签与下单记录分两次写入，标签写入时间戳必须早于成交时间戳，否则标 `label_post_hoc=1`，分析时单独分组。

### 4.2 约束二：标签需可交叉验证

标签是自评，可以撒谎或自欺。用行为代理变量做一致性检查：

| 标签 | 交叉验证信号 | 矛盾示例 |
|---|---|---|
| `normal` | 同日交易笔数 | 标 normal 但当日第 5 笔 |
| `normal` | 前笔结果 | 标 normal 但前一笔刚止损且间隔 <30 分钟 |
| `revenge` | 仓位大小 | 标 revenge 且仓位大于均值 1.5 倍，标签可信 |
| `bored` | 是否在候选池内 | 标 bored 且 `was_in_candidate=0`，标签可信 |

矛盾率本身就是一个指标：**标签矛盾率高，说明自我觉察能力弱，这比标签内容更有诊断价值。**

## 5. Trading DNA：采纳，加失效机制

用户提议的 Trading DNA 模块采纳，这是从"测量执行"到"认识自己"的必要一跃。

但必须加两个机制，否则会变成危险的自我实现预言。

### 5.1 风险：DNA 标签的自我强化循环

```
AI 输出「你趋势持仓能力强」
    ↓
你更倾向做趋势单
    ↓
趋势单样本增多，震荡单样本减少
    ↓
下一版 DNA 更强化「趋势能力强」
    ↓
你的能力圈实际在收窄，但 DNA 显示在强化
```

这与 §1.2 阻断 CIO 的是同一类问题（反馈环污染），只是这次污染对象是人的认知而非系统参数。

### 5.2 冻结的两个机制

**机制一：DNA 有效期**

每版 DNA 标注 `valid_until`（默认 6 个月）与 `sample_window`。过期自动作废，需用新样本重算。禁止无限期沿用。

**机制二：DNA 必须附反证条件**

每条 DNA 结论强制附带失效条件，格式对齐既有 Decision Log 的 `invalidation` 字段设计：

```
结论：趋势持仓能力强（n=43，2025-02~2026-08，含趋势/震荡两种环境）
反证：若未来 20 笔中趋势单胜率 <45%，本条作废
状态：active
```

无反证条件的 DNA 结论不予输出。这与既有「§14 信号带 validation_status」纪律一致。

### 5.3 DNA 输出门槛

按市场独立计数，且要求环境多样性：

| 市场 | 样本门槛 | 环境要求 |
|---|---|---|
| MT5 | ≥100 笔 | 含趋势 + 震荡两种行情 |
| ASHARE | ≥60 笔 | 含上涨 + 震荡 + 下跌三种 regime |

用户 2026-08-04 调整立场：**DNA 是结果不是目标**，分阶段演进，早于门槛生成=「早期自我标签」风险：

- 0–100 笔：只记录，不归纳
- 100–300 笔：只发现模式，不贴身份
- 300 笔以上：生成 Trading DNA v1.0

本冻结的 per-market 硬下限（MT5≥100 / ASHARE≥60）与用户分阶段过程纪律不冲突，后者是前者的前置护栏。

## 6. 排期冻结：与用户建议的分歧

用户建议顺序：`B0 MT5导入 → B2 结果分析 → A股采集 → Coach 行为分析`。

**这一条我反对；用户 2026-08-04 已接受并行方案（采信"采集连续性 > 历史丰富性"），分歧解除。**

### 6.1 反对依据：时间惩罚不对称

| | A股采集 | MT5 导入 |
|---|---|---|
| 数据是否已存在 | **否**，未来产生 | **是**，历史已存在 |
| 延后一个月的代价 | **永久损失一个月样本，不可补录** | 零，下个月导一样 |
| 启动成本 | 每天 2 分钟 | 一次性 10 分钟 + 1 天开发 |

MT5 历史数据放在那里不会腐烂。A股每一个没记录的交易日，数据永久消失，且**事后回忆的计划是假的**，无法补造。

把 A股采集排在 MT5 分析之后，等于用"零收益的等待"换取"永久性的数据损失"。

### 6.2 更硬的依据：记录中断已发生过

实测 `exec_result` 标记分布：

| 日期 | 信号数 | missed 标记 |
|---|---|---|
| 07-20 | 10 | 10 |
| 07-21 | 15 | 15 |
| 07-23 | 15 | 15 |
| 07-29 | 36 | **0** |
| 07-30 | 15 | **0** |
| 07-31 | 20 | **0** |
| 08-03 | 10 | **0** |

**标记只持续了 3 天就停止。** 07-29 当天信号量突增到 36 条，标记同时中断，两件事大概率相关。

这说明记录习惯极其脆弱。中断后重启的成本远高于持续维持。当前 A股侧记录已经处于中断状态，再等 MT5 分析做完（乐观估计 2-3 周）才重启，重启失败概率显著上升。

### 6.3 冻结的排期：并行，不串行

```
立即（本周）
├── A0  exec_result 三态化，恢复每日标记        每天 2 分钟，你操作
└── B0  跑 mt5_export.py 导出历史              一次 10 分钟，你操作

其后
├── A1  trade_execution 建表 + CLI 录入
└── B1  MT5 CSV 导入器

再其后
├── B2  MT5 结果分析（胜率/期望值/R分布/持仓时长/时段拆分）
└── B3  用 B2 结论反推 A股侧该重点记录什么

最后（受铁律排期约束）
└── 分析层 L1 及以上
```

A 线与 B 线并行，互不阻塞。A0 和 B0 都是你的操作，加起来今天就能做完。

### 6.4 与既有铁律的关系

不变：采集层不受 8 周冻结约束（冻结范围为日报信息生产扩张 + Layer1 评分模型，Trader OS 采集层两者都不碰）；分析层排在 `月报v0.2 → 全球资产接入 → 日报优化` 之后。

## 8. 冻结的开放问题

以下问题在得到答案前，相关模块不得开工：

| # | 问题 | 阻塞对象 | 获取方式 |
|---|---|---|---|
| 1 | MT5 历史成交笔数与时间跨度 | B1/B2 全部 | 跑 `mt5_export.py`，10 分钟 |
| 2 | A股月均实际交易笔数 | A股侧 DNA 是否立项 | 你估算即可 |
| 3 | 两市场哪个是主要痛点 | 资源投向 | 你的判断 |

## 11. 架构第一原则：Capture > Analysis（2026-08-04 拍板）

用户确立：先拥有数据，再分析；不追求完美数据。这是 Trader OS 的最高优先级约束，高于任何分析层美观度。

**实证依据**：exec_result 标记 07-20/21/23 有、07-29 起全空，信号量同日突增到 36——证明问题不是意愿，是系统设计超过行为承载能力。采集系统再次断掉，是本模块头号风险，高于一切算法问题。

**v0.1 最小记录闭环（≤60 秒/笔）**，交易结束后：
- 是否执行？（executed / skipped）
- 是否计划内？（planned: y/n）—— 驱动 Execution Fidelity
- 交易方向？（buy / sell）
- 一句理由？（可选，留空=NULL）

其余全部自动化，不增加手动负担。Decision State（§4）为最低优先级可选，增加负担立即删除。

**不可违反**：任何让单次记录 >60 秒的设计，视为违反本原则，必须回退。
